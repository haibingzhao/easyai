# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- ReAct Agent Loop with 3-phase tool execution and context overflow self-healing
- DAG-based Swarm orchestration (SINGLE / TEAM / DELIBERATION task types)
- AI Deliberation Debates with neutral judge and autonomous convergence
- Leader-Member reactive teams with structured decision protocol
- AI Config Generator — natural language to complete Agent/Workflow configs
- Incremental context compaction with usage-aware token estimation
- Defense-in-depth permission system with shell command safety classification
- Shadow Git snapshots with author attribution and file-level revert
- Async MCP integration (Stdio + StreamableHTTP transports)
- Channel-based SSE event streaming with 15+ typed events
- JWT authentication with RS256 and refresh token rotation
- Desktop app (Electron + bundled JRE + embedded H2)
- Web console (React 18 + TypeScript + TailwindCSS 4)
- File-based memory system with LLM-powered flush
- Observability module (Micrometer Tracing + OpenTelemetry)
- Chat surface preferences per owner — the default agent for a fresh chat and the agents hidden from the composer picker, stored per personal or shared group bucket (`GET`/`PUT /api/chat-preferences`, `chat_preference` table, Settings → Chat Agents). Hidden ids must be enabled chat agents and at least one chat agent stays visible.
- Tasks page deep link to a host's own result page: a `TASK_TYPE_REGISTRY` entry can declare `link(task)`, built from the row's `payload`/`result`, and the row plus detail dialog offer that navigation (`TaskLink { labelKey, path }`). Returning null renders no button, so a type whose handler writes no `result` keeps the generic row.
- Knowledge library is now a folder tree: nested folders with derived display paths, articles addressed by a stable id and placed in a folder (`GET/POST/PATCH/DELETE /api/knowledge/folders`, `POST /api/knowledge/article/move`), and the console gets a resizable tree with folder create/rename/delete, move, and upload-into-folder. A default "Uncategorized" folder is created on first write.
- Article lifecycle: drafts vs published, retrieval toggle (`ragEnabled`) with per-article index pending state, and a console editor with publish/unpublish/reindex. Only published, retrieval-enabled articles are readable through `knowledge_search`/`knowledge_read`.
- Application isolation now lives on the account: `app_user.owner_app` is the single source of truth, usernames are unique per application, every JWT carries an `app` claim, and background work (`async_task` orphans, watch schedules, scheduled task settings, temp-workspace sweeps) is scoped by joining `user_id` to accounts of the current `spring.application.name`. The per-row `owner_app` columns on `async_task`, `watch` and `project` are gone (`V41__owner_app_on_app_user.sql`).
- Skills are safe when two applications share one data directory: `SkillSyncService` takes a per-owner file lock under `{rootDir}/.locks` on top of the in-process mutex, and `SkillIndexer` leases a catalog row (`next_attempt_at`) before a background reconcile so a second host skips it.
- A host application now declares its own memory taxonomy instead of the framework carrying it: implement `DomainCatalogContributor` (`domain` + `memoryCategories`) as a Spring bean in the host repo, select it with `easyai.domain`, and `DomainCatalog` resolves the active domain. Framework ships only `coding`; an `easyai.domain` nobody declares fails startup with the registered domains listed rather than falling back.
- `@easyai/console` exports two host extension points for vocabulary: `registerTranslations(language, entries)` and `registerKnowledgeCategories(specs)`, so an application's category labels and knowledge picker live in its own console.

### Changed

- MCP row-addressed endpoints (`/connect`, `/disconnect`, `/tools`, `/prompts`) now default to the caller's personal bucket; shared rows must pass `?scope=group`. `McpServerDto` and `AgentDto` now expose `ownerId`.
- Hiding a chat agent now only trims the picker; an existing conversation keeps its selected agent. Changing the configured default agent only affects new chats — a conversation pins its agent on the first message.
- `UserStore` is application-scoped: `findByUsername`, `findById` and `count` take `ownerApp`, and `User` gained a required `ownerApp`. Hosts that implement the store or construct `User` (including test doubles) must update and recompile. `JwtTokenProvider` now takes the application name; `AuthService` and the account-aware stores take a `HostIdentity`, auto-wired by the framework. Row-level host plumbing is gone: `AsyncTask`/`Watch`/`ProjectInfo.ownerApp`, `AsyncTaskDto.ownerApp`/`controllable`, `WatchForeignHostException`, `HostStartupGate`, `HostProperties` and `LegacyOwnerAdopter` no longer exist, and `WatchService`/`WatchTaskHandler`/`WatchTaskScheduler`/`DefaultWorkspaceService`/`TaskController`/`AsyncTaskLifecycle` dropped their `host`/startup-gate parameters, so host code that builds or catches these must recompile.
- `@easyai/console` declarations no longer ship the internal `@/*` alias: `build:lib` post-processes `dist-lib/**/*.d.ts` (`scripts/fix-lib-alias.mjs`) and rewrites every alias specifier to a relative path. A host used to resolve none of those imports, so the whole cross-file type surface degraded to `any` — registry callbacks (`title` / `summarize` / `link`) now arrive contextually typed and need no parameter annotations at the call site.
- Knowledge API and SPI are reshaped around ids and folders: `key`/`knowledgeKey`/`source`/`relativePath` are gone (`id` + `folderId` instead), `POST /api/knowledge/save-text` takes `folderId`, unpublish is `DELETE /api/knowledge/article?id=…`, `KnowledgeFolderDto` gained `writable`, and `KnowledgeAccessPolicy` dropped `filterReadable`/`canReadEntry`/`canManageEntry` (added `canManageFolders`). `KnowledgeStore` no longer exposes `list`/`detail`/`update`/`uploadBatch`/`batchDelete`; hosts implementing the policy or the store, or building these DTOs, must recompile.
- `DELETE /api/tasks` (bulk clear) now removes all of the caller's rows; application isolation comes from the account, so a caller never sees another application's tasks.
- `MemoryType` is a value type carrying only the storage directory name (`{code}/{name}.md`); it is no longer an enum with a `domains` set, and `entriesFor`/`fromDirName` are gone. Which categories exist, which the LLM may write and which the UI offers is the active domain's `DomainCatalog`. Stored entries whose code is not in the active catalog now parse and list instead of being dropped, so memory written by another application stays readable.
- `DomainCatalog` is an auto-configured bean, not a global object; `CategoryController` (`GET /api/system/categories`) answers `{domain, memory}` and no longer publishes knowledge categories. Knowledge article `category` stays a free-form tag the backend neither validates nor enumerates, so the framework holds no `KnowledgeType` and no knowledge taxonomy.
- `memory_list`'s filter values and `memory_write`'s accepted types are now both generated from the active domain's catalog (the list tool used to advertise a stale `user/feedback/project/reference` set).
- Trading's memory and knowledge categories left the framework: the memory set is `TradingDomainCatalog` in easyai-trading, the knowledge picker and its Chinese labels are in trading-console. The framework no longer contains `market_insights`, `strategy_lessons`, `risk_rules`, `market_data`, `broker_connectors` or `risk_compliance` outside tests that assert they are rejected.
- `scheduled_task_setting` is now keyed by `(user_id, task_type, schedule_key)` (`V42__scheduled_task_setting_multi_row.sql` rebuilds the table), so one user can own several independent schedules of the same type — e.g. trading's daily-analysis plans. `ScheduledTaskSettingStore` gained `list(user, type)`, `get`/`delete` take an optional schedule key (default `''` = the legacy single row), and `listForScheduling` takes a composite `(user, schedule key)` cursor; the runner keeps one timer per row. Hosts implementing the store must add `list` and recompile.
- `easyai.tasks.scheduled.zone` (default: the JVM zone) now interprets cron expressions when a row has no persisted `schedule_zone`, and drives the host-owned polling window. Trading sets `Asia/Shanghai`.
- The default watch run budget is now 300 s and 30 agent-loop iterations (`easyai.watch.run-timeout-ms` / `easyai.watch.max-iterations`; formerly 180 s / 12). A multi-source check routinely spends over two minutes in slow tool calls, and one slow fetch was parking otherwise healthy runs `TIMED_OUT`; deployments can still override both properties.

### Fixed

- A cancelled model stream now stops its producer. The producer runs on its own `SupervisorJob`, so a task timeout (or a user stop) used to leave the agent loop calling the model and tools, and writing into the shared session, after the row was already parked `TIMED_OUT`; `EventStream.result()` now cancels the producer, and watch runs drain the event flow so a long run does not retain every delta.
- The task transcript page slices a watch's shared audit session to the firing the task opened. A timed-out firing used to render with the next firing's messages and final answer beneath its own error header; a retry that failed before writing a new prompt now renders no messages instead of the previous attempt's.

### Upgrade Notes

- `V36__knowledge_tree_schema.sql` is destructive: it drops `knowledge_article`/`knowledge_folder` and rebuilds them around folders. Pre-release knowledge data is wiped; there is no migration of old articles. The old EasyRAG documents keyed `easyai:{source}/{relativePath}` are **not** removed by the migration — wipe that knowledge bucket (e.g. `u_<user>_k`) before or after the upgrade, or old hits will occupy the top-K and be filtered out again, making search look empty.
- `V41__owner_app_on_app_user.sql` moves isolation from rows to accounts: it adds `app_user.owner_app` and constrains it `NOT NULL` in the same script, replaces the global username index with `(owner_app, username)`, drops `owner_app` from `async_task`/`watch`/`project`, and replaces the old due index with `watch(status, next_due_at)`. **Upgrade order:** stop every application sharing the database; run `ALTER TABLE app_user ADD COLUMN IF NOT EXISTS owner_app VARCHAR(64)` with psql (the same statement V41 runs, so it is repeatable); backfill every account; only then start the new builds, which apply V41 and its constraint. An account left without an application is refused at login and never executes background work, so rows are backfilled first and a leftover NULL makes V41 fail loudly at startup instead — fix the rows, then clear the recorded failure (`flyway repair` on PostgreSQL) and restart.
- `V42__scheduled_task_setting_multi_row.sql` rebuilds `scheduled_task_setting` with a `(user_id, task_type, schedule_key)` primary key; existing rows keep `schedule_key=''`. A host that starts writing several rows per type must disable or delete the legacy `''` row, or it keeps firing alongside the keyed rows. Implementing `ScheduledTaskSettingStore` now requires `list(user, type)`, and `listForScheduling` callers must pass `afterUserId` and `afterScheduleKey` together or neither.
- Accounts, and therefore `async_task`/`watch`/`project`/`scheduled_task_setting` rows, are now isolated by application: `system` rows and rows whose `user_id` has no `app_user` entry no longer take part in background scans (orphan parking, watch firing, scheduled settings, temp-workspace sweeps). Reassign or delete such rows before the upgrade. An auth-disabled deployment writes every row under `system`, so it has no background execution at all. Historical rows written by an account that used to sign in to more than one application follow that account to the application it is assigned to — audit `watch.allowed_tools` and the account's task/project rows before assigning one. A username may exist once per application, so the same person needs a separate account to sign in to two applications.
- Every application on a shared database must set an explicit, stable `spring.application.name`; the Boot default `application` is refused at startup. JWT access, refresh and script tokens now carry that name as an `app` claim and are rejected by any other application. All tokens minted before the upgrade lack the claim and become invalid: users must sign in again.
- Hard cut: after `V41` the previous build cannot run (the three columns no longer exist and Flyway refuses a database newer than its scripts). Stop and upgrade home-api / trading-api / agent-api / desktop together; rolling a new and an old build side by side is not supported. Keep a `pg_dump` before migrating — rollback means restoring the backup and the old build.
- Desktop clients using the H2 file database must have their accounts assigned before the first start of the new build, because `V41` enforces `owner_app NOT NULL`: open the file and run `ALTER TABLE app_user ADD COLUMN IF NOT EXISTS owner_app VARCHAR(64); UPDATE app_user SET owner_app='easyai-desktop-server' WHERE owner_app IS NULL`, or delete the H2 file to reinitialise (pre-release data, including session history, is lost).
- The order of `V36` and `V37` relative to existing knowledge data is fixed by Flyway; `V38` adds the `knowledge_article.folder_id → knowledge_folder.id` foreign key and fails loudly if dangling rows already exist (inspect them before upgrading). `V37` is historical: its row-level columns are removed by `V41`, so `easyai.host.adopt-legacy-rows` and the `LegacyOwnerAdopter` startup claim no longer exist.
- Skill sync now writes `{rootDir}/.locks/{owner}.lock`; keep that directory writable and out of skill discovery (it is a dot directory). Two applications sharing the *same* root directory are serialized by it; separate root directories are independent by design.
- Backend and every host consuming the console `dist-lib` must be released together. If staged, upgrade the backend first: old clients lose group-row `connect`/`disconnect`/`tools`/`prompts` (404), while a new console against an old backend cannot address MCP rows (no `ownerId`) and cannot edit group Chat settings. In that degraded state the console treats MCP rows as personal, hides the group target, and keeps same-named rows read-only instead of guessing a bucket.
- `AgentDto.ownerId` is a required constructor parameter, so host code that builds `AgentDto` itself must be updated and recompiled.
- **Breaking for host applications:** the framework now ships only the `coding` memory taxonomy. Every deployment whose `easyai.domain` is not `coding` must contribute a `DomainCatalogContributor` bean in its own repo and recompile, or it fails at startup with `Unknown easyai.domain '…'`. Trading does this with `TradingDomainCatalog`, Easy Home with `HomeDomainCatalog`. Backend, console `dist-lib` and every host must be released together: a new console against an old backend keeps its coding knowledge presets and loses nothing, while an old console against a new backend would lose its knowledge category list.
- A consolidation task queued before the upgrade whose `type` is not in the rebuilt catalog fails visibly (`not part of the active domain catalog`) instead of running an empty pass; memory files themselves are untouched — storage keys are unchanged, so no migration is needed.
